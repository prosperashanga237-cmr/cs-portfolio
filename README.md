Prosper Inventory — Project Three: App Functionality and Launch Plan

This submission is the completed, functional build of Prosper Inventory, a small-business inventory tracking app for Android. It includes the SQLite-backed login and inventory management code developed in Project Three, built on top of the UI design first created in Project Two.

Briefly summarize the requirements and goals of the app you developed. What user needs was this app designed to address?

Prosper Inventory was built for small retail shop owners, boutique sellers, and warehouse or stockroom staff who were tracking stock with spreadsheets or paper counts. The core requirement was a simple way to log in, see every item’s current quantity at a glance, adjust that quantity as stock moves, add or remove items, and be alerted automatically the moment something runs out, without needing to actively watch the app. The underlying user need was reducing the mental overhead of manual stock tracking: a shop owner shouldn’t have to remember to check inventory constantly or dig through a spreadsheet to find out something is out of stock.

What screens and features were necessary to support user needs and produce a user-centered UI for the app? How did your UI designs keep users in mind? Why were your designs successful?

The app has five screens: Login, Create Account, the Inventory grid, Add Item, and SMS Notification Settings. The inventory grid uses a two-column card layout with quantity controls and a delete action directly on each card, so the most common actions (adjusting or removing stock) never require navigating away from the main screen. The design kept users in mind by minimizing steps for frequent tasks while isolating rarer or riskier ones: adding an item gets its own dedicated screen since it is a deliberate, occasional action, while deleting an item requires a confirmation dialog specifically because it is destructive and shouldn’t happen from a single accidental tap. The designs were successful because every screen maps directly to one of the user needs above rather than existing for its own sake, and the consistent Material Design color system and card-based grouping make the app’s state legible at a glance.

How did you approach the process of coding your app? What techniques or strategies did you use? How could those techniques or strategies be applied in the future?

I approached development by separating concerns into small, single-purpose classes rather than putting all the logic in one Activity: a DatabaseHelper class owns all SQLite access, a plain InventoryItem class models one row of data, and an InventoryAdapter only knows how to display that data and forward taps back to the Activity. This made each piece easy to reason about and test independently, and it meant a change to, say, the database schema never risked breaking the UI code. I also designed the SMS notification feature so that it degrades gracefully: the rest of the app works identically whether or not the user grants SMS permission, since no other feature depends on that choice. Both strategies, isolating responsibilities into small classes and designing optional features so their absence doesn’t break anything else, are ones I plan to keep using on any future app, since they make a codebase much easier to extend without introducing new bugs elsewhere.

How did you test to ensure your code was functional? Why is this process important, and what did it reveal?

I tested using the Android Emulator throughout development rather than only at the end: validating XML resource references and ID/string cross-references before every build, running the login and registration flow with both valid and invalid input, and using the emulator’s Extended Controls to simulate changing conditions where needed. For the SMS feature specifically, I tested both branches of the permission flow, granted and denied, to confirm the rest of the app kept working either way. This process matters because a feature that “looks right” in the layout editor can still fail at runtime from something like a missing resource reference or an unhandled permission state; testing early revealed exactly that kind of issue before it could compound into a harder-to-diagnose bug later in development.

Consider the full app design and development process from initial planning to finalization. Where did you have to innovate to overcome a challenge?

The clearest challenge was reconciling an SMS alert feature with a core constraint: the app had to remain fully functional for a user who denies the SMS permission. Rather than treating permission handling as an afterthought bolted onto the notification screen, I built a small dedicated helper class that silently and safely no-ops whenever permission or a saved phone number is missing, so the “happy path” and the “permission denied path” are both first-class outcomes the rest of the app never needs to know about. That let the inventory grid’s code stay simple, it just calls one method after a stock change, without needing any permission-awareness of its own.

In what specific component of your mobile app were you particularly successful in demonstrating your knowledge, skills, and experience?

The SQLite database layer is the component I’m most proud of. It implements full Create, Read, Update, and Delete operations across two tables (users and inventory items) behind a clean, well-documented API, handles edge cases like duplicate usernames without crashing, and keeps the UI layer completely decoupled from the raw database/cursor logic. It’s the piece of the app that most directly demonstrates the database and persistence concepts from this course applied to a real, working feature rather than an isolated exercise.
